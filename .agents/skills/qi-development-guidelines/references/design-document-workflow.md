# 设计文档工作流

本参考文件用于实现需求前提炼设计约束。只有任务涉及已有设计文档或需要新增架构结构时才需要完整阅读。

## 1. 发现文档

从仓库根目录开始检查：

```bash
rg --files -g 'AGENTS.md' -g 'DESIGN.md' -g '*design*.md' -g 'README.md' -g '*.yaml' -g '*.yml'
```

按“最近目录优先、根目录兜底”的顺序读取：

1. 当前目录和目标包目录下的 `AGENTS.md`。
2. 目标包目录或父目录中的 `DESIGN.md`。
3. 目标包的 `README.md`、配置示例和相关测试。
4. 根目录 `AGENTS.md` 与全局项目说明。

文档中的示例路径可能因重命名或迁移过时。此时保留设计意图，使用当前真实包路径，并记录差异。

## 2. 提炼约束

实现前至少记录以下内容：

| 维度 | 要回答的问题 |
| --- | --- |
| 目录结构 | 新代码应该放在哪个包？是否规定了文件名、子目录或分层？ |
| 职责边界 | 当前包负责什么？明确不负责什么？ |
| 数据流 | 输入、状态变化、持久化和输出的顺序是什么？ |
| 一致性 | 哪些操作必须原子、幂等、可重试或 fail-closed？ |
| 生命周期 | 谁创建、持有、关闭连接、goroutine、timer 和 provider？ |
| 错误语义 | 哪些错误必须保留身份、包装、映射或对外隐藏？ |
| 安全要求 | 是否涉及 token、密码、个人数据、日志脱敏或权限边界？ |
| 兼容性 | 是否需要兼容旧 key、旧 token、旧配置或已有 API？ |
| 验收标准 | 文档要求哪些测试、构建、竞态检查或运行验证？ |

## 3. 处理冲突

- 需求明确覆盖设计文档时，按用户最新要求实施，但在代码和交付说明中标出破坏性影响。
- 设计文档与现有代码不一致时，不要静默选择；优先遵循更近、更具体、更新明显的文档，并检查测试和调用方是否已迁移。
- 文档只描述目标、没有规定实现细节时，可以选择保守实现，但不得改变包边界或引入未声明的业务职责。
- 文档引用不存在的目录时，先确认当前模块迁移后的对应目录；只有无法安全映射时才请求澄清。

## 4. 设计到代码的映射

实现前形成类似下面的映射：

```text
需求：支持认证 session 的 refresh rotation
设计依据：internal/shared/auth/DESIGN.md
目标目录：internal/shared/auth/
核心文件：manager.go、refresh.go、scripts.go
必须保持：Redis 原子轮换、旧 token 失效、session 过期上限
测试位置：internal/shared/auth/*_test.go
```

实现完成后逐项核对映射，不要只以“编译通过”作为完成标准。

## 5. 交付检查

- 新文件位于设计规定的目录，包依赖方向符合边界。
- 设计中的“不负责”事项没有被顺手塞进基础设施包。
- 成功、失败、取消、重复调用和资源关闭路径都有明确行为。
- 设计要求的测试已补充并实际运行。
- 交付说明包含设计依据、主要变更、验证结果和仍存在的文档/代码差异。
