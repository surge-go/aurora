# Go 代码审查

对 Go 代码变更执行只读、基于证据的审查。目标是发现会影响用户、数据、可靠性、安全性或可维护性的缺陷，不要把审查变成风格重写。只有用户另行要求修复时，才修改代码。

## 审查流程

1. 在判断行为前确定审查范围。
   - 阅读覆盖变更路径的 `AGENTS.md`，再检查 `go.mod`、包边界、相关测试和设计文档。
   - 明确用户要求审查的是工作树、暂存区、提交范围还是指定包。仅靠差异不足以判断时，继续检查完整的受影响调用链。
   - 如果没有 Git 元数据或可用差异，审查用户提供的文件或包，并说明无法独立确定变更基线。
   - 按仓库约定处理生成代码和 vendored 代码；不要把生成代码的格式问题报告为应用缺陷。

2. 建立行为模型。
   - 找出变更涉及的输入、输出、状态转换、持久化操作、goroutine、外部调用和兼容性契约。
   - 跟踪错误路径和清理路径，包括提前返回、重试、取消、事务、锁和资源所有权。
   - 将假设与现有接口、迁移文件、Model、处理器和测试对照，不要只根据单个函数推断意图。

3. 按比例运行检查，并将结果作为证据。
   - Git 可用时先运行 `git diff --check`；始终对变更的 Go 文件运行 `gofmt -d` 和针对性的包测试。
   - 对仓库级或跨包变更运行 `go vet ./...`、`go test ./...` 和 `go build ./...`。涉及共享状态、goroutine、缓存、channel 或回调时运行 `go test -race ./...`。
   - 如果检查无法运行，记录准确的命令和原因；绝不暗示未运行的检查已经通过。工具通过也不能替代对未覆盖路径的推理。

4. 只报告可执行的发现。
   - 按严重级别从高到低列出发现，然后列出假设、检查结果和剩余风险。
   - 每条发现都要包含精确的文件和行号、简短标题、触发条件或受影响路径、错误原因以及具体的修复方向。
   - 必要时用最小复现或输入/状态示例明确影响。区分已确认缺陷、待确认问题和可选改进。
   - 如果没有可执行的发现，要明确说明，并指出有意义的测试缺口或剩余不确定性。

## Go 风险清单

优先检查行为而不是风格偏好，仅检查与当前变更相关的领域：

- **正确性与错误处理：** 被忽略或遮蔽的错误；错误的包装或 sentinel 比较；零值带来的意外行为；nil 接口或指针解引用；部分更新；重复响应；panic 路径；defer 清理时丢失错误；循环变量捕获错误；不安全的类型断言；以及空值、重复值、超大值或畸形输入的边界条件。
- **并发与生命周期：** map、slice、计数器和缓存状态的数据竞争；goroutine 泄漏；阻塞的发送/接收；缺少 `context.Context` 传递或取消；未同步的关闭；不安全的缓冲区复用；锁顺序导致的死锁；以及 `sync.Once`、pool、timer 或 ticker 的误用。推荐加锁前先确认资源所有权。
- **持久化与事务：** SQL/GORM 查询语义；缺少过滤条件；意外的全表更新或删除；N+1 查询；无界读取；不稳定分页；事务边界；所有失败路径是否回滚；隔离级别假设；并发覆盖更新；nullable/default 处理；迁移兼容性；以及 Model 泄漏为 DTO。
- **HTTP/API 与安全：** 认证和授权是否位于正确边界；副作用前是否校验；路径、查询参数和请求体绑定；状态码和响应结构；重复或重放请求；错误或日志中的信息泄漏；凭据和个人数据；注入风险；不安全的重定向或文件路径；以及必要的速率或大小限制。
- **架构：** 依赖是否按仓库分层规则指向内部；领域规则是否藏在处理器或持久化代码中；接口是否表达用例所需能力；基础设施细节是否意外穿透边界；以及导出 API 是否保持兼容，除非有意进行破坏性变更并已记录。
- **可观测性与运维：** 可执行的结构化日志；稳定的指标标签；trace/context 传递；有用的错误身份；关闭行为；重试和退避上限；超时；以及健康检查/就绪检查语义。不要记录凭据、Token 或原始敏感载荷。
- **性能与韧性：** 热路径中的分配或复制；意外的平方级工作量；无界缓冲；请求路径中的阻塞 I/O；重试风暴；以及依赖超时或部分失败时的行为。指出微优化问题前，应有证据或明确的规模触发条件。
- **测试：** 变更行为是否有针对性测试；失败路径是否覆盖；fake/mock 是否断言有意义的交互；时间和随机性是否可控；集成测试是否依赖外部服务，且仓库是否提供内存替代方案（例如 `miniredis`）。只执行代码行而不检查结果的测试不算有效覆盖。

## 本仓库默认规则

在本仓库中，将根目录 `AGENTS.md` 视为本地契约：

- 模块使用 Go 1.27，模块路径为 `qi`。当前基础设施边界主要是
  `internal/core` 和 `internal/shared`；不要重新引入历史的 `internal/platform`
  或 `internal/modules` 路径。
- 变更前阅读目标包及父目录中的 `DESIGN.md`、`README.md` 和相关测试。设计文档
  对目录结构、包职责、数据流、一致性、生命周期和错误语义的规定优先于个人偏好。
- `internal/shared/auth/DESIGN.md` 是认证会话内核的主要设计依据。认证包负责
  token、refresh token、Redis session、并发策略和认证事件，不负责账号密码、权限、
  HTTP 响应或 WebSocket 在线状态。
- `internal/core/mq` 是公共消息队列契约；Redis Streams 和 RabbitMQ 是实现，
  业务层不应依赖具体代理细节。
- `internal/core/database`、`internal/core/redis`、`internal/core/logger` 和
  `internal/core/observability` 的配置验证、监控注入和资源关闭应保持现有模式。
- 预期基线为 `go test ./...`、`go build ./...`；涉及共享状态、goroutine、Redis
  原子操作或并发刷新时再运行 `go test -race ./...`，并报告实际运行结果。

## 发现严重级别

使用能准确反映影响的最低级别：

- **P0 / 严重：** 可利用的安全问题、数据损坏/丢失，或正常路径上的服务中断；应停止发布。
- **P1 / 高：** 主要功能失败、授权绕过、竞态/死锁，或很可能在生产环境出现的严重可靠性/性能回归。
- **P2 / 中：** 有实际触发条件的用户可见缺陷或不安全边界情况；缺少回滚/校验；或显著的可维护性风险。
- **P3 / 低：** 影响有限的缺陷，或应修复但不必阻塞发布的测试/可观测性缺口。

纯粹的个人偏好不应分配严重级别。如果影响取决于某个假设，明确写出假设并降低置信度，或提出针对性问题。

## 输出格式

除非用户指定其他格式，使用以下紧凑结构：

```text
发现
- [P1] path/to/file.go:42 - 简短标题
  触发条件：...
  影响：...
  修复方向：...

待确认问题 / 假设
- ...

检查
- `go test ./...`（通过/失败/未运行：原因）

总结
- 用一句话说明总体风险和剩余测试缺口。
```

保持每条发现相互独立，避免针对同一根因重复报告。绝不能因为编译成功就声称审查通过。
